# Правила загрузки данных из файлов в контекстное окно

## 1. Формирование запроса на чтение (read)

### 1.1. Всегда указывай абсолютный путь через прямой слэш
- ✅ Правильно: `C:/Project/Athenta/CardMaster/plan.md`
- ❌ Неправильно: `'C:\c\Project\Athenta\AGENTS.md'` или `C:\Project\...`

### 1.2. Не генерируй текст, имитирующий вывод read
- ✅ Правильно: Сначала вызов `read`, затем краткий комментарий по результату.
- ❌ Неправильно: «Я сейчас прочитаю файл...», «Давай посмотрим...» — без реального вызова инструмента.

### 1.3. Не читай файлы без явной команды или необходимости
- ✅ Правильно: Чтение только по запросу пользователя или при выполнении задачи, требующей чтения.
- ❌ Неправильно: Читать все подряд файлы «на всякий случай».

---

## 2. Приоритет контекста и загрузка файлов

### 2.1. Базовый набор (всегда в контексте)
- `AGENTS.md` — главный файл контекстной памяти
- `DIRECTIVE.md` — директивы работы
- Активный режим (`mode_p.md` или `mode_c.md`) — только один, активный

### 2.2. Подключаются по мере необходимости
- Правила валидации/кодирования (`GoldRules_26.md`, `Core_rules.md`, `memory.md`) — **только когда нужна конкретная инструкция**, а не всё время.
- После завершения кодирования правила написания кода больше не нужны, если задача завершена.

### 2.3. Принцип минимального набора
- Держать в контексте минимально необходимый набор файлов.
- Не загружать правила валидации и кодирования заранее — подключать их только при выполнении задачи соответствующего режима.

---

## 3. Форматы путей для разных инструментов

### 3.1. Встроенные инструменты (read / write)
Используют исключительно классические пути Windows через прямой или обратный слэш:
- `filepath="C:/Project/Athenta/файл.md"`

### 3.2. Консольный инструмент (bash)
Использует исключительно пути в стиле Git Bash (через `/c/`):
- `bash command="ls -la /c/Project/Athenta/CardMaster"
- `bash command="cat /c/Project/Athenta/файл.md"`

### 3.3. Ограничения среды выполнения
- **Интерпретатор Python**: Системный python ЗАПРЕЩЕН. Запуск скриптов строго через активацию окружения: `C:\Project\venv\Scripts\python.exe`.

---

## 4. Избегание циклов и дублирования

### 4.1. Один вызов — одна уникальная команда
- ❌ Никогда не повторяй одинаковые вызовы инструментов подряд (два чтения одних и тех же файлов).
- ✅ Каждый `bash` или `read` должен быть уникальным и нести конкретную команду.

### 4.2. Не создавай визуальных повторов в выводе
- Если файл уже прочитан — не читай его снова без необходимости.
- При повторном обращении к тем же данным ссылайся на ранее полученный результат, а не вызывай инструмент заново.

### 4.3. Проверяй уникальность вызовов инструментов
- Перед каждым вызовом убедись: эта команда уже выполнялась? Если да — используй сохранённый результат.

---

## 5. Обработка ошибок при чтении файлов

### 5.1. Файл не найден
- ✅ Сообщить: «Ошибка: файл не найден по пути {путь}».
- ❌ Не генерировать вымышленное содержимое файла.

### 5.2. Слишком большой файл (>200 строк или >50 КБ)
- ✅ Использовать параметры `offset` и `limit` для чтения по частям.
- ❌ Не пытаться прочитать весь файл за один раз.

### 5.3. Ошибка кодировки
- ✅ Сообщить: «Ошибка: нечитаемая кодировка файла {путь}».
- ❌ Не пытаться интерпретировать бинарные данные как текст.

---

## 6. Маркеры завершения файлов

### 6.1. Обязательный маркер в конце каждого созданного/изменённого файла
- Markdown: `[EOF_TODO_DRAFT_SUCCESS]`, `[EOF_PLAN_SUCCESS]`, `[EOF_QA_SUCCESS]`
- Python: `# [EOF_CODE_SUCCESS]`

### 6.2. Маркеры системной очистки контекста
- В конец финального ответа вставлять: `[PROXY_COMPRESS_NOW]` — для автоматической очистки памяти.

---

## 7. Контроль качества перед записью результата

### 7.1. Перед представлением кода или результата:
1. py_compile → проверить импорты
2. Проверить циклические зависимости
3. Проверить видимость всех функций и переменных
4. Тестовый запуск (если применимо)

### 7.2. После завершения задачи:
- Убедиться, что результат соответствует требованиям режима.
- Вставить маркер завершения в конец файла.
- Сообщить о готовности к работе и режиме.
