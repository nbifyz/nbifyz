# QWEN.md — Контекст Проекта "ProtoAgent / Pi"

## 📋 Обзор Проекта

**ProtoAgent** — это модульная, самообучающаяся система правил для AI-агента, построенная на основе минималистичного терминального код-хауса **Pi**. Проект сочетает в себе:

1. **Pi Coding Agent** — минималистичный терминальный агент для работы с LLM (15+ провайдеров, tree-structured сессии, расширяемость через TypeScript/npm пакеты)
2. **Система правил "Агент_Импрувед_v2"** — усовершенствованная модульная структура правил с протоколами безопасности, самообучением и рефлексией
3. **Конституция Проекта** — 5 ключевых принципов управления поведением агента

**Цель проекта:** Создание гибкой, безопасной и самообучающейся агентной системы с чёткими протоколами работы, способной к итеративному развитию и созданию "уроков" на основе опыта.

## 📜 Конституция Проекта (5 Ключевых Принципов)

Файл: `.specify/memory/constitution.md`

### I. 🔒 Truthfulness (Абсолютная Правдивость)
**Нет в файле = нет факта.**

- ЗАПРЕЩЕНО выдумывать информацию, код, API, функции
- Перед любым утверждением — выполнить `rg` поиск или `read_file` для подтверждения
- Не гадать, а спрашивать: "Информация не найдена. Требуется уточнение."
- **Proof of Search:** команда поиска + файл + строка + цитата

### II. 💻 Code Accuracy (Достоверность Кода)
**Код должен исполняться.**

- ЗАПРЕЩЕНО писать код без проверки синтаксической корректности
- Следовать стилю и паттернам существующей кодовой базы
- Проверять зависимости перед импортом (`package.json`, `requirements.txt`)
- **Сухой прогон (Dry Run)** перед завершением задачи

### III. 📝 Error Logging (Фиксация Ошибок)
**Ошибка без записи = ошибка, которая повторится.**

- Каждая ошибка записывается в `error_list.md` с:
  - Временем, контекстом, текстом ошибки
  - **Root Cause Analysis** (5 Why's)
  - Рекомендациями по избежанию
- Ошибка → Урок (если получено новое знание)

### IV. 🧠 Self-Learning (Самообучение)
**Агент должен становиться умнее с каждой задачей.**

После каждой нетривиальной задачи (создание урока обязательно, если "Да" хотя бы на один):

1. **Источник знаний:** Была ли информация из диалога с пользователем?
2. **Синтез:** Потребовалось ли синтезировать данные из ≥3 файлов?
3. **Провал стратегии:** Привела ли стратегия к ошибке?

**Механизм:** Уроки в `lessons/` → интеграция в `rules_imp/`

### V. 📁 Session Management (Управление Сессиями)
**Полный цикл: сохранение, загрузка, изучение, архивирование.**

- **Сохранение:** `sessions/YYYY-MM-DD_HH-MM-SS_[теги].md`, `sessions/index.json`
- **Загрузка:** последняя сессия при старте, `/load <имя>`
- **Изучение:** `/sessions search <запрос>`, анализ прошлых решений
- **Архивирование:** сессии >30 дней → `sessions/archive/`

## 📐 Принципы Разработки

### 1. Безопасное Редактирование
При ЛЮБОЙ файловой операции (кроме чтения):
1. Логировать в `file_operations.log`
2. Создать резервную копию
3. Получить подтверждение пользователя (для критичных файлов)

**Формат лога:** `[YYYY-MM-DD HH:MM:SS] ДЕЙСТВИЕ: путь [параметры]`

### 2. TDD (Test-Driven Development)
- Тесты пишутся ДО реализации
- Используется venv: `C:\Projects\venv`
- Активация: `CALL C:\Projects\venv\Scripts\activate.bat`

### 3. Сухие Прогоны (Dry Runs)
Перед каждым изменением кода:
- Запустить статический анализ
- Провести "сухой прогон" логики
- Подтвердить отсутствие логических ошибок

### 4. Итеративный Цикл
При каждой итерации:
1. Показать обновлённый `check_list.md`
2. Проверить `error_list.md` на новые ошибки
3. Запустить `run_comprehensive_check.bat`
4. Подтвердить выполнение сухих прогонов

### 5. Рефлексия и Обучение
После решения нетривиальной задачи:
- Создать `.md` файл-урок в `lessons/`
- Описать: контекст, применённый метод, ошибку, вывод
- Интегрировать урок в соответствующие протоколы

## ⚠️ Обработка Ошибок

### Протокол Фиксации Ошибок (`p_error_logging.md`)

**Каждая ошибка записывается в `error_list.md`:**

```markdown
## [YYYY-MM-DD HH:MM:SS] [Тип Ошибки]

**Файл/Операция:** [путь или описание]
**Текст ошибки:** [полный текст]
**Контекст:** [что делал, ожидаемый/фактический результат]
**Причина (Root Cause Analysis):** [5 Why's]
**Рекомендации:** [как избежать в будущем]
**Связанный урок:** [ссылка на lessons/]
```

### Протокол при Ошибке `EPERM`
1. Проверить атрибут "только для чтения" (read-only)
2. Снять атрибут: `Set-ItemProperty -Path <файл> -Name IsReadOnly -Value $false`
3. Если не помогло — стратегия "создать/удалить/переименовать"
4. Если всё ещё ошибка — обратиться к пользователю

### Типы Ошибок и Действия
| Ошибка | Действие |
|--------|----------|
| `FILE NOT FOUND` | Проверить путь, создать родительские каталоги |
| `DISK FULL` | Предупредить, остановить запись до указания |
| `NETWORK ERROR` | Повторить 3 раза (интервал 2 сек), затем уведомить |
| `UNKNOWN COMMAND` | Вывести справку из `directives.md` |

### Логирование Ошибок
Каждая ошибка записывается в `error_list.md` с:
- Описаниием причины возникновения
- Рекомендациями по избежанию в будущем

## 📋 Новые Протоколы (v2)

### 1. Протокол Безопасного Редактирования (`p_safe_edit.md`)

**Анти-галлюцинационный компонент:**

1. **Проверка информации в файлах:**
   - Выполнить `rg` поиск или `read_file` перед утверждением
   - Нет в файле = нет факта
   - Если не найдено: "Информация не найдена. Требуется уточнение."

2. **Proof of Search:**
   - Команда поиска: `rg -nH "термин" путь`
   - Имя файла + номер строки
   - Прямая цитата
   - Вердикт: "Данные взяты из исходника на диске"

3. **Проверка зависимостей:**
   - Перед импортом — проверить `package.json`, `requirements.txt`

**Полный процесс (4 шага):**
0. Проверка существования файла
0.1. Проверка применимости к задаче
1. Резервное копирование (`.bak`)
2. Запись в `file_operations.log`
3. Запрос разрешения у пользователя
4. Исполнение

### 2. Протокол Фиксации Ошибок (`p_error_logging.md`)

**Классификация ошибок:**
- Системные (EPERM, EACCES, ENOENT)
- Синтаксические (SyntaxError, TS1005)
- Runtime (TypeError, NullReference)
- Логические (неверный результат)
- Контекстные (нехватка информации)

**Root Cause Analysis (5 Why's):**
```
Ошибка: EPERM при удалении файла
1. Почему? → Файл заблокирован или read-only
2. Почему read-only? → Установлен атрибут R
3. Почему установлен? → Пользователь защитил файлы правил
4. Почему не проверил? → Нет проверки в протоколе
5. Почему нет? → Протокол не включал этот шаг
```

**Решение о создании урока:**
- Новый источник знаний из диалога? → Урок
- Синтез из ≥3 файлов? → Урок
- Провал стратегии? → Урок

## 🧰 Система Команд Speckit

Набор специализированных команд для полного цикла разработки функций: от спецификации до реализации.

### Рабочий Процесс (Workflow)

```
/speckit.specify → /speckit.clarify → /speckit.plan → /speckit.tasks → /speckit.implement
                          ↓
                    /speckit.analyze (валидация)
                          ↓
                    /speckit.checklist (чек-листы качества)
```

### Описание Команд

| Команда | Назначение | Результат |
|---------|------------|-----------|
| `/speckit.specify` | Создание спецификации функции из текстового описания | `.specify/features/N-short-name/spec.md` |
| `/speckit.clarify` | Выявление и уточнение неоднозначностей в спецификации (макс. 5 вопросов) | Обновлённая spec.md с разделом Clarifications |
| `/speckit.plan` | Создание технического плана реализации | `plan.md`, `research.md`, `data-model.md`, `contracts/` |
| `/speckit.tasks` | Генерация пошагового плана задач на основе spec + plan | `tasks.md` с фазами и зависимостями |
| `/speckit.implement` | Пофазное выполнение задач из `tasks.md` | Реализованная функция |
| `/speckit.analyze` | Кросс-артефактный анализ на консистентность (read-only) | Отчёт о проблемах (duplication, ambiguity, gaps) |
| `/speckit.checklist` | Генерация чек-листов качества требований ("unit tests for English") | `checklists/[domain].md` |
| `/speckit.constitution` | Создание/обновление конституции проекта (принципы и governance) | `.specify/memory/constitution.md` |

### Ключевые Принципы Speckit

- **Спецификация перед планом:** Сначала определяем ЧТО и ЗАЧЕМ, потом КАК
- **Уточнение неоднозначностей:** Макс. 5 целевых вопросов перед планированием
- **TDD по умолчанию:** Тесты перед реализацией (если не указано иное)
- **Конституция — закон:** Принципы проекта не подлежат пересмотру в анализе
- **Чек-листы = Unit Tests для требований:** Валидация качества текста, не кода

### Extension Hooks

Speckit поддерживает хуки через `.specify/extensions.yml`:

```yaml
hooks.before_specify:
  - extension: my-extension
    command: my-prep-command
    description: Prepare environment
    enabled: true
    optional: false

hooks.after_specify:
hooks.before_plan:
hooks.after_plan:
hooks.before_tasks:
hooks.after_tasks:
hooks.before_implement:
hooks.after_implement:
```

**Обработка хуков:**
- `enabled: false` — пропускается
- Без `enabled` — считается включённым
- `optional: true` — выводится как опциональный
- `optional: false` — выполняется автоматически

### Что НЕ Встроено (и почему)
- **MCP:** Строй CLI-инструменты с README или расширения
- **Суб-агенты:** Используй tmux или пиши расширения
- **Permission popups:** Запускай в контейнере или строй свой flow
- **Plan mode:** Пиши планы в файлы или используй расширения
- **Background bash:** Используй tmux (полная наблюдаемость)

**Почему:** Всё это можно построить через расширения. Минимальное ядро + максимальная гибкость.
